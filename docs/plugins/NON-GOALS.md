# 不该做什么（明确不提供，也不接受相关需求）

这些不是"还没做"，是**方向上排除**：没有接口、没有桩、没有配置面。
照着别家生态（Bukkit/Forge/Sponge 那类引擎内插件）的想象提需求前，
请先读这一页。判断依据见
`knowledge/0007-v2-extension-candidate-survey.md`（X/A 类）与
`knowledge/0010-plugin-v2-implementation-status.md`。

## 1. 引擎内部流：不提供

击杀、伤害、经济、单位位置、存活状态等对局内实时数据**不在契约内**。

为什么：引擎是闭源的，Avalon 对这些数据没有可靠的真值来源；造一个
"尽力镜像"的接口只会产出死字段和错误数据。契约的 `PlayerInfo` 因此
只有身份字段，没有战绩字段——这不是占位，是明确拒绝。
（对局内现有的两个否决点 `unit.operation` / `factory.build` 是治理面
拦截指令包，不是引擎状态读取。）

## 2. 运维命令拦截：不提供

插件不能拦截或审计控制台运维命令（`internal/util/game/command/command.go::HandleMessageWith`
没有拦截接缝）。

为什么：加拦截点是结构性改动，且运维命令是服务器的最后控制手段——
它必须对第三方故障免疫。运维动作的可观察面用事件表达
（封禁有 `player.banned` 等，踢出有 `player.kicked`），不用命令钩子。

## 3. 插件 → 玩家写通道：不提供

插件不能主动给玩家发消息、踢人、禁言。

为什么：这等于把玩家体验的写权限交给第三方进程，权限边界无法收敛。
如果将来要做，它会是一个**新的、需要单独授权模型的 Avalon HTTP 面**，
不是在现有事件契约上加字段。

## 4. 插件 → Avalon 查询通道：不提供

插件不能主动查房间列表、玩家状态。

为什么：同 3——现有契约严格单向（Avalon 调用插件）。查询通道意味着
Avalon 要再开一个服务端面并设计读权限模型，属另一件产品事项。
你需要的状态，事件载荷里已经给了。

## 5. relay 侧事件：不提供

relay 协议的玩家进出、relay 房间关闭等不在事件目录。

为什么：relay 路径没有现成的发射点，属于新开发而非接线；等真有运营
需求再评估。

## 6. JVM 内加载：永不

引擎壳（Avalon-Helper）不加载任何第三方代码，没有 jar 插件位，将来
也不会有。

为什么：引擎闭源且按字节码改造运行，第三方代码进 JVM 等于把崩溃域
和攻击面直接接进游戏内核。插件只存在于治理面（Avalon，Go 进程之外
的独立进程）。

## 7. 下载与自更新：永不

Avalon 运行期不下载、不执行插件产物；没有静默自更新。

为什么：分发必须内容寻址（GitHub Releases + SHA-256 校验和），禁止
绑定个人域名——运行期自动拉取会把供应链风险直接变成服务器风险。
插件的安装 = 运营手动部署进程 + 手动登记 `/data/Plugins.json`。

## 8. mod 扩展：不提供

mod 归闭源引擎解析，Avalon 只负责文件落位与一致性校验（引擎单位
checksum）。不要为 mod 设计插件接口。

---

**如果你的需求落在这八条里**：先问"事件目录里有没有等价的观察面"，
再问"能不能在插件侧用已有事件推导"。两者都不行，说明它需要新的
产品决策（新的 Avalon 面 + 授权模型），而不是契约加字段。
